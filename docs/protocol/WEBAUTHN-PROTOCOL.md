# WebAuthn protocol

Use @simplewebauthn/browser and @simplewebauthn/server. API boundaries/lifecycle are defined in architecture. Sources: https://simplewebauthn.dev/docs/packages/server and https://simplewebauthn.dev/docs/packages/browser (reviewed 2026-10-12).
WEBAUTHN_RP_ID, WEBAUTHN_ALLOWED_ORIGINS and LUXIA_RUNTIME_MODE are mandatory startup configuration. Incoming Origin selects only an explicitly trusted exact entry; Referer/Host/forwarded headers never select runtime or trust configuration. Architecture owns the centralized runtime/cookie policy: HTTPS and Secure __Host cookies in staging/production; explicit loopback-only development/test exception.
Registration: generate random provisional UUID, require discoverable credential and UV, attestation none, persist purpose/RP/origin/TTL/binding hash. Foundation V1's immutable server-owned services/api/algorithm-policy.ts permits only ES256 (-7) and RS256 (-257). Pass that same policy to options generation and registration verification; Ed25519 (-8) and unknown algorithms deny regardless of library support/defaults. Verify through library with requireUserVerification=true, then insert new identity, public credential and audit atomically. No existing-user attachment route.
Authentication: require UV; discoverable credential resolves user. Verify stored public key, signature, RP hash, exact origin, expected consumed challenge, userHandle, counter, revocation and active security state. Update counter and mint session transactionally. No browser success before API verified=true.
Challenge lifetime is five minutes, single-use, bound to a random HttpOnly flow cookie. One outstanding browser flow is supported; requesting new options replaces the cookie.
The HTTP shape boundary requires object body/response/clientExtensionResults, nonempty bounded id/rawId and clientDataJSON, type=public-key, and the ceremony's nonempty bounded attestationObject or authenticatorData/signature. It does not substitute for cryptographic verification. Missing/wrong-shaped fields, unparseable clientDataJSON or missing/invalid challenge cannot identify a safe attempt and deny without consumption; the legitimate browser may still submit a valid request for that challenge. A wrong binding/origin/purpose/RP or expired challenge does not consume someone else's valid challenge.
Once shape parsing and atomic binding checks identify a legitimate attempt, consumption commits before cryptographic verification. Crypto or subsequent transaction/audit failure leaves the challenge burned. A successful attempt also burns it. Any retry after consumption denies and requires new options; an existing flow cookie cannot resurrect a consumed challenge. Never let an unrelated binding burn another browser's challenge.
User-facing wording: Device verification, User verification or Passkey verification. Never infer Face ID, fingerprint modality or physical device identity from generic UV.
